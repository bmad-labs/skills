2. Purpose

The design documents are read as instructions by three readers:

  • the builder Agent, which decides what to implement and what to leave alone;
  • the planner Agent, which plans the next Story;
  • the tests, which check what a sentence promises.

A wrong sentence causes one of two faults.

FaultConsequenceExample in this batch
A sentence describes work that is not done The reader checks for an output that does not exist. A later builder assumes the work is present, so it is omitted or duplicated. The cleanup job note claimed it deletes expired invitations and notifies their senders. It does neither.
A sentence omits a fact that is needed The reader has no answer and must infer one. Two readers can infer differently. No document stated where a notebook's sharing state is read from, so the rule "hide notes in a revoked share" had no input.

3.1 The workspace admin can join a shared notebook your decision clauses 6, 8, 10

Current
A shared notebook holds its owner and invited collaborators. The membership rule requires every member to hold an invitation, and the workspace admin holds none, so the API refuses the share.
After
The rule reads: every invited collaborator holds an invitation, and the workspace admin may join without one. The member list holds three members.
Reason
The support process requires collaborators to ask for access help in the notebook's own thread and the admin to answer there. Without this clause, Story 4.1 cannot create a shared notebook.
Observed by
Workspace admin, both collaborators.

3.2 An edit lock records the revision the edit starts from your decision clauses 14, 15

Current
The edit lock holds the user id only. When a save arrives the API must compare the note's current revision with the revision the edit started from, and no record holds that revision.
After
The lock also records the rev the edit starts from. The API can then name the changes that belong to this edit.
Reason
A save cannot be checked for conflicts without a start point, and a shared note cannot accept a second editor without that check. The change adds one value to each lock.
Observed by
API, API clients through the save response, planner Agent.

Before

User opens note 42
lock: user_id = u-17
      (no base revision)
   │
   ▼
Client edits offline
   │
   ▼

revision anywhere  ✗

After

User opens note 42
lock: user_id = u-17
      base    = rev 8
   │
   ▼
Client edits offline
   │
   ▼
API receives the save:
compare rev vs base rev 8
→ changes of this edit  ✓

3.3 A refused share names the check that failed your decision clauses 11, 12, 18

Current
Seven checks gate a share request. Three return a message. Four — unverified invitee, existing member, archived notebook, blocked invitee — return none, so the client cannot tell what to fix. The written order also lists the seat-limit check before the suspension check, while the code checks suspension first.
After
One message names the failing check. The written order matches the code.
Reason
A refused client needs the reason to act on it. A written order that contradicts a tested order causes the next builder to break that test.

API clients, workspace admin, tests.

3.4 A token that requested a revoked share is not renewed your decision clauses 7, 16

Current
The access check denies the request and writes an audit entry. No record marks the token, so the next refresh renews it.
After
The denial also sets a yes/no mark on the token record. The next refresh refuses to renew that token and asks the client to sign in again.
Reason
The rule "a token that touched a revoked share is never renewed" has no record to read, so it cannot be enforced or tested. Story 4.6 needs the mark for its test.
Observed by
API. The client signs in again at the next refresh.

Before

Client requests a revoked notebook
   │
   ▼
access check denies, writes an audit entry
   │
   ▼
next refresh: token renewed
with its previous scopes
   │
   ▼
session continues,
no record of the attempt

After

Client requests a revoked notebook
   │
   ▼
access check denies, writes an audit entry
   │  + marks the token
   ▼
next refresh: marked token
NOT renewed
   │
   ▼
client signs in again,
previous token dropped

8. Decisions

  1. decision Apply the fourteen proposed clauses? All fourteen, the ones that block a Story, or none.
  2. decision Admin in a shared notebook. May the workspace admin join a shared notebook without an invitation? If not, the support process changes instead and Story 4.1 reads differently.
  3. decision Base revision. May an edit lock record the revision the edit starts from? One value per lock.
  4. decision Revoked-share mark. Two options: set the mark on any denied request, so that token is not renewed at the next refresh; or leave the mark unset until an abuse detector is built as its own Story.
